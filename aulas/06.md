# #06 - Validação de Dados e Tratamento de Erros

Na Aula 05, finalizamos o CRUD e separamos controllers de services. Nesta aula, vamos consolidar os contratos da API: validar dados de entrada com Zod, representar falhas esperadas com erros da aplicação e devolver respostas de erro consistentes.

# Validação de Dados

## Por que validar dados de entrada?

Dados recebidos por HTTP são externos e não confiáveis, mesmo quando a requisição veio de uma interface criada por nós. A validação no servidor impede que dados malformados avancem para a regra de negócio e para o banco, reduz erros em cascata e permite explicar ao cliente como corrigir a requisição.

Ela não substitui as demais defesas. O Prisma usa consultas parametrizadas, reduzindo o risco de injeção SQL, mas XSS exige codificação de saída no contexto em que o texto será exibido; autorização, limites de tamanho e tratamento seguro de arquivos são controles diferentes. Em Node.js, *buffer overflow* não é uma ameaça típica do JavaScript gerenciado — não o use como exemplo de problema resolvido por um schema.

## Princípios de validação

1. **Não confie na entrada.** A validação do frontend melhora a experiência, mas pode ser ignorada por uma chamada direta à API.
2. **Falhe cedo e de modo seguro.** Rejeite dados inválidos antes de executar a operação.
3. **Prefira allowlists.** Defina tipos, faixas, tamanhos e valores aceitos; não tente apenas bloquear palavras “perigosas”.
4. **Use defesa em profundidade.** Cada camada protege uma responsabilidade diferente.

| Camada | Responsabilidade neste projeto |
| --- | --- |
| Cliente | Feedback rápido para UX; nunca é a única validação. |
| Middleware Zod | Forma, tipos, limites e transformação do HTTP recebido. |
| Service | Regras de negócio e existência de relações. |
| Banco | `NOT NULL`, `UNIQUE`, chaves estrangeiras e última linha de defesa. |

## Validação sintática e semântica

**Sintática** verifica estrutura: `email` é texto e possui formato de e-mail, `id` é inteiro positivo, `dificuldade` está entre 1 e 3. É o papel principal do Zod nesta aula.

**Semântica** verifica o significado no domínio: o e-mail já está cadastrado? O professor informado existe? A matéria possui questões e, por isso, não pode ser removida? Essas regras continuam nos services porque dependem do estado da aplicação e do banco.

> A mesma entrada pode ser sintaticamente válida e semanticamente inválida. `professorId: 42` tem formato válido, mas precisa existir no banco.

# Tratamento de Erros

## Erros operacionais e erros de programação

- **Operacionais:** condições previstas do domínio ou da requisição, como dados inválidos, recurso ausente e conflito de e-mail. A API deve responder com um status 4xx e mensagem segura.
- **De programação ou infraestrutura:** bugs, falhas inesperadas e indisponibilidade de dependências. O servidor registra o contexto para diagnóstico, mas responde com uma mensagem genérica de status 500.

## Contrato de erro padronizado

Todas as respostas de erro desta aula terão a mesma estrutura:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Dados de entrada inválidos",
    "details": [
      { "field": "email", "message": "Email inválido" }
    ]
  },
  "timestamp": "2026-09-04T12:00:00.000Z",
  "path": "/users"
}
```

`code` é estável para programas clientes; `message` é apropriada para pessoas; `details` existe principalmente em validações. Não incluiremos `stack`, mensagem de banco ou `requestId` na resposta porque ainda não há middleware que gere um identificador de requisição.

| Situação | Status | Código |
| --- | --- | --- |
| Schema, corpo, query ou parâmetro inválido | 400 | `VALIDATION_ERROR` |
| Recurso ou relação inexistente | 404 | `NOT_FOUND` |
| Estado incompatível, como e-mail duplicado | 409 | `CONFLICT` |
| Falha inesperada | 500 | `INTERNAL_ERROR` |

## Middleware centralizado

Um middleware de erro possui quatro parâmetros: `(error, req, res, next)`. Ele deve ser registrado depois das rotas. Em Express 5, uma exceção ou rejeição de uma função `async` de rota é encaminhada para o tratamento de erro; ainda assim, encaminhar explicitamente com `next(error)` torna o fluxo didático visível.

O handler também deve respeitar `res.headersSent`: se a resposta já começou, o Express precisa assumir a finalização padrão.

## 2. Criar os erros da aplicação

Crie `src/errors/AppError.js`:

```js
/**
 * Representa um erro operacional que pode ser comunicado pela API.
 */
export class AppError extends Error {
  /**
   * @param {string} message - Mensagem segura para o cliente.
   * @param {number} statusCode - Status HTTP associado ao erro.
   * @param {string} code - Código estável para consumidores da API.
   * @param {Array<{field?: string, message?: string}>} details - Detalhes opcionais.
   */
  constructor(message, statusCode = 500, code = "INTERNAL_ERROR", details = []) {
    super(message);
    this.name = this.constructor.name;
    this.statusCode = statusCode;
    this.code = code;
    this.details = details;
    this.isOperational = true;
  }
}

/**
 * Erro para dados de entrada inválidos.
 */
export class ValidationError extends AppError {
  /**
   * @param {string} message - Resumo do problema de validação.
   * @param {Array<{field: string, message: string}>} details - Erros por campo.
   */
  constructor(message = "Dados de entrada inválidos", details = []) {
    super(message, 400, "VALIDATION_ERROR", details);
  }
}

/**
 * Erro para recursos que não existem.
 */
export class NotFoundError extends AppError {
  /**
   * @param {string} message - Mensagem do recurso ausente.
   */
  constructor(message = "Recurso não encontrado") {
    super(message, 404, "NOT_FOUND");
  }
}

/**
 * Erro para estados incompatíveis com a operação solicitada.
 */
export class ConflictError extends AppError {
  /**
   * @param {string} message - Mensagem do conflito.
   */
  constructor(message = "Conflito de dados") {
    super(message, 409, "CONFLICT");
  }
}
```

## 3. Criar o middleware de validação e o handler de erro

Crie `src/middlewares/validate.js`:

```js
import { ValidationError } from "../errors/AppError.js";

/**
 * Cria um middleware que valida e substitui dados HTTP pelos valores parseados.
 * @param {import("zod").ZodType} schema - Schema Zod a aplicar.
 * @param {"body"|"params"|"query"} source - Fonte dos dados da requisição.
 * @returns {import("express").RequestHandler} Middleware de validação.
 */
export default function validate(schema, source = "body") {
  return (req, _res, next) => {
    const result = schema.safeParse(req[source]);

    if (!result.success) {
      const details = result.error.issues.map((issue) => ({
        field: issue.path.join(".") || source,
        message: issue.message,
      }));

      return next(new ValidationError("Dados de entrada inválidos", details));
    }

    req[source] = result.data;
    return next();
  };
}
```

Crie `src/middlewares/errorHandler.js`:

```js
import { AppError, NotFoundError } from "../errors/AppError.js";

/**
 * Encaminha rotas não encontradas para o mesmo contrato de erro da API.
 * @param {import("express").Request} req - Requisição recebida.
 * @param {import("express").Response} _res - Resposta Express não utilizada.
 * @param {import("express").NextFunction} next - Próximo middleware.
 * @returns {void}
 */
export function notFoundHandler(req, _res, next) {
  next(new NotFoundError(`Rota ${req.method} ${req.originalUrl} não encontrada`));
}

/**
 * Formata erros operacionais e protege detalhes internos em falhas inesperadas.
 * @param {Error} error - Erro recebido do pipeline Express.
 * @param {import("express").Request} req - Requisição que causou o erro.
 * @param {import("express").Response} res - Resposta Express.
 * @param {import("express").NextFunction} next - Handler padrão do Express.
 * @returns {void}
 */
export default function errorHandler(error, req, res, next) {
  if (res.headersSent) {
    return next(error);
  }

  if (error instanceof AppError && error.isOperational) {
    return res.status(error.statusCode).json({
      success: false,
      error: {
        code: error.code,
        message: error.message,
        ...(error.details.length > 0 && { details: error.details }),
      },
      timestamp: new Date().toISOString(),
      path: req.path,
    });
  }

  if (error?.code === "P2002") {
    return res.status(409).json({
      success: false,
      error: { code: "CONFLICT", message: "Registro duplicado" },
      timestamp: new Date().toISOString(),
      path: req.path,
    });
  }

  console.error("Erro inesperado", { method: req.method, path: req.path, error });
  return res.status(500).json({
    success: false,
    error: { code: "INTERNAL_ERROR", message: "Erro interno do servidor" },
    timestamp: new Date().toISOString(),
    path: req.path,
  });
}
```

## 4. Criar schemas do usuário

Crie `src/schemas/userSchema.js`:

```js
import { z } from "zod";

const papelSchema = z.enum(["PROFESSOR", "ADMIN"], {
  message: "Papel deve ser PROFESSOR ou ADMIN",
});

const fotoSchema = z.union([
  z.string().trim().url("URL da foto inválida"),
  z.null(),
]);

/** Schema para POST /users. */
export const createUserSchema = z
  .object({
    nome: z.string().trim().min(3, "Nome deve ter pelo menos 3 caracteres").max(100, "Nome deve ter no máximo 100 caracteres"),
    email: z.string().trim().toLowerCase().email("Email inválido"),
    papel: papelSchema.optional(),
    foto: fotoSchema.optional(),
  })
  .strict();

/** Schema para PATCH /users/:id. */
export const updateUserSchema = z
  .object({
    nome: z.string().trim().min(3, "Nome deve ter pelo menos 3 caracteres").max(100, "Nome deve ter no máximo 100 caracteres").optional(),
    email: z.string().trim().toLowerCase().email("Email inválido").optional(),
    papel: papelSchema.optional(),
    foto: fotoSchema.optional(),
  })
  .strict()
  .refine((data) => Object.keys(data).length > 0, {
    message: "Envie pelo menos um campo para atualização",
  });

/** Schema para parâmetros :id positivos. */
export const idParamSchema = z.object({
  id: z.coerce.number().int("ID deve ser inteiro").positive("ID deve ser positivo"),
});
```

## 5. Refatorar o service e o controller de usuários

No `src/services/userService.js`, preserve os `select`s públicos da Aula 05 e converta resultados de domínio em erros. Exemplos centrais:

```js
import prisma from "../config/database.js";
import { ConflictError, NotFoundError } from "../errors/AppError.js";

/**
 * Atualiza um usuário existente depois de conferir unicidade de e-mail.
 * @param {number} userId - ID já validado pelo middleware.
 * @param {{nome?: string, email?: string, papel?: "PROFESSOR"|"ADMIN", foto?: string|null}} data - Campos permitidos.
 * @returns {Promise<object>} Usuário público atualizado.
 * @throws {NotFoundError} Quando o usuário não existe.
 * @throws {ConflictError} Quando outro usuário já possui o e-mail.
 */
export async function updateUser(userId, data) {
  const user = await prisma.user.findUnique({
    where: { id: userId },
    select: { id: true, email: true },
  });

  if (!user) {
    throw new NotFoundError(`Usuário com ID ${userId} não encontrado`);
  }

  if (data.email && data.email !== user.email) {
    const owner = await prisma.user.findUnique({ where: { email: data.email } });
    if (owner) {
      throw new ConflictError("E-mail já cadastrado");
    }
  }

  return prisma.user.update({
    where: { id: userId },
    data,
    select: publicUserSelect,
  });
}
```

No controller, o middleware já entregará `req.params.id` como número e `req.body` normalizado. Cada handler apenas delega ao service e encaminha falhas:

```js
/**
 * Atualiza parcialmente um usuário.
 * @param {import("express").Request} req - Requisição com dados já validados.
 * @param {import("express").Response} res - Resposta HTTP.
 * @param {import("express").NextFunction} next - Encaminhador de erros.
 * @returns {Promise<void>} Resposta de atualização ou encaminhamento de erro.
 */
export async function update(req, res, next) {
  try {
    const user = await userService.updateUser(req.params.id, req.body);
    res.status(200).json({ success: true, message: "Usuário atualizado com sucesso", data: user });
  } catch (error) {
    next(error);
  }
}
```

Repita o padrão para criar, listar, buscar e remover. `getUserById` deve lançar `NotFoundError`; `createUser` deve lançar `ConflictError` para e-mail duplicado; `deleteUser` deve lançar `ConflictError` se existirem matérias ou questões vinculadas. O middleware traduzirá cada erro em HTTP.

## 6. Registrar validação, app e servidor

Em `src/routes/userRoutes.js`, mantenha `PATCH` e aplique os schemas:

```js
router.post("/", validate(createUserSchema), userController.create);
router.get("/", userController.getAll);
router.get("/:id", validate(idParamSchema, "params"), userController.getById);
router.patch("/:id", validate(idParamSchema, "params"), validate(updateUserSchema), userController.update);
router.delete("/:id", validate(idParamSchema, "params"), userController.remove);
```

Em `src/app.js`, mantenha as rotas de usuários, matérias e questões. Depois delas, registre `notFoundHandler` e `errorHandler`:

```js
app.use("/users", userRoutes);
app.use("/subjects", subjectRoutes);
app.use("/questions", questionRoutes);
app.use(notFoundHandler);
app.use(errorHandler);
```

`src/server.js` deve continuar apenas iniciando `app.listen(...)`. Os testes importam `app.js`, nunca `server.js`.
